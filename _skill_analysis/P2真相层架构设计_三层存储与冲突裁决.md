## 0. 一页结论（TL;DR）



1. **md / JSON / SQLite 不是三选一，是三层**：

* **md = 血肉（SSOT）**：叙述、长文本，人读人改、git diff、LLM 原生消费。

* **JSON = 关节**：配置与流程状态，小而嵌套、程序可靠读，**零运行时依赖**。

* **SQLite = 骨骼（只读投影）**：大量同构真相实体的精确查询 / 聚合 / 强约束，二进制、可重建、机器层零 LLM token。

1. **单写双读**：人和 S4 档案员**只写 md（及少量 JSON 配置 / 流程态）**；truth.db 由确定性脚本从 md **单向、全量构建**，Agent **只读不写**，gitignore、丢了可 rebuild。

2. **真相不做知识库**：BM25/ZVEC 知识库是 "召回层"，只解决相关性（近似、可漏可错、无事务、无当前值），**只供线索、不裁决、不阻断**。事实的权威当前值只能由 md SSOT + 结构化一致性层决定。

3. **冲突检查可多方，登记裁决只有一个出口**：事中 schema 硬拦 + 事后 verify/S3 + 召回供线索；**登记唯一出口 = S4 单点串行写 md + Change Report（append-only，带 evidence\_ids）**。

4. **v5.4 已证伪 "db 取代 md"（方案 B）**，双写（方案 C）必然漂移；本方案是**方案 A（md 单写 + db 只读投影）**，并针对 v5.4 三个死因做修正。

5. **分期**：

* **v1.9.2（零依赖，先做）**：角色八问 + md 真相活跃 / 归档分区 + JSON checkpoint/hash + 输入包 token 自统计。**不引入数据库。**

* **P2（等瓶颈证据再写码）**：truth.db 只读投影，分 P2.1 当前态强约束 / P2.2 历史快照 / P2.3 取数切换三步。

* 写码门槛：批跑到 **100–300 章**，用 "输入包 token 自统计" 数据证明 md 读取确已成瓶颈，再动 P2。

## 1. 背景与要解决的问题

### 1.1 超长篇的根本矛盾

真相状态（角色生死 / 位置 / 知识、物品持有、伏笔、时间线、关系）随章数单调增长。S1 编剧每章都要据此规划，于是陷入二选一（长篇问题域清单 F 组高频反馈）：



* **全量读** → 上下文爆炸，token 不可持续；

* **压缩 / 总结后读** → 细节失真，"前面火属性后面水属性"" 死者复活 ""伏笔撒了忘收"。

两书批跑（无人工介入连写）已在 20–30 章规模复现真相类事故：



| 事故                                                | 书名 | 本质           |
| ------------------------------------------------- | -- | ------------ |
| h\_007 重复登记两条                                     | 唐末 | 唯一性无约束       |
| 第 3 章正文存在但未落库、缺 Change Report，第 30 章却宣称 "30 章全落库" | 唐末 | 流程状态失真、无原子性  |
| timeline 只登记 2 行，滞后 28 章                          | 唐末 | 状态更新漏做、无门禁   |
| 数据 / 肉身、人数、距离、年代多套口径互打                            | 星尘 | 无 "设定宪法" 权威值 |
| 第 17/18 章同一穿越事件两个互斥版本并存                           | 星尘 | 事件状态无单点定稿    |
| 角色后期晚章 "复活"、物品凭空出现 / 消失                           | 两书 | 跨章一致性失效      |

### 1.2 现有防线与短板



* 已有：md 真相 SSOT（6 文件）+ verify.py 正则门禁（#23 实体冲突 / #28 伏笔债务 / #32 进度跳号等）+ S3 语义检验（Q6/Q7）+ S4 原子四步。

* 短板：

1. **正则脆弱**：靠解析 md 表格文本，口径分散在 verify.py 数百行，新增约束成本高；

2. **事后才查**：脏数据在落库后才被扫到，而非写入瞬间被约束拒绝；

3. **md 越大读取代价越高**：门禁能查错，但不能降低 S1 每章的读取量；

4. **缺少历史快照**：md 只存 "当前态一行"，查 "第 N 章时林野知道什么" 要翻散落的 Change Report。

### 1.3 待决策的三个问题



1. 真相文件要不要做成 SQLite？

2. 真相文件能不能做成知识库（RAG / 向量）？

3. md、JSON、SQLite 各放什么？冲突谁检查、谁登记？

## 2. v5.4 实证：纯 SQLite 走过，而且失败了

> 旧包 
>
> `novel-writer-jy-v5.4-full.zip`
>
>  是作者自研的
>
> **真 SQLite**
>
>  版本；novel-engine（纯 md）正是从它退回的产物。这不是推测，是自己的历史实验，结论权重最高。

### 2.1 v5.4 的实现事实



* 每本书一个业务库 `database.db`（22 张表）+ 全局只读知识库 `writing_knowledge_seed.db`（15 张表、数千条技法）。

* `migrate --from-markdown` 单向迁移，**md 备份后弃用 = db 取代 md（方案 B）**。

* 7 步流水线，前 6 角色只读、**Settler 唯一写库**；`queries.md` 是标准 SQL 模板库，**让 Agent 照着裸写 INSERT/SELECT 执行**。

* `scripts/` 只有 5 个小脚本（hook/checkpoint/ 字数 / 标点 / 视角，Python 内置 sqlite3），其余 17 张表**没有脚本，靠 Agent 自己跑 SQL**。

* 库路径**硬编码** `Path.home()/novels/书名/database/database.db`。

* schema **无硬外键**（原文："SQLite 弱类型，依赖关系由应用层保证"），relationships/events 等大量字段是 **TEXT 里塞 JSON**。

* **无 "无 Python 降级"，无 "导出给人看" 机制**；人侧只有 recap.md 与 checkpoint JSON。

### 2.2 五个死因（为什么被放弃）



1. **人瞎了**：真相在二进制库里、无导出，无法肉眼排查 / 手改（本次两书排查全靠直接打开 md）。

2. **跨宿主瘫了**：17 张表靠 Agent 裸写 SQL，网页 chat / 无代码执行宿主直接不可用；路径硬编码、项目不自包含。

3. **没吃到 SQLite 最该有的好处**：无外键 + JSON TEXT，一致性仍靠 Agent 自觉 ——**背上二进制黑箱代价，没拿到强约束收益，两头不讨好**。

4. **无降级**：没有 Python/sqlite 执行能力时全链路瘫痪。

5. **git 无法 diff** 二进制库，变更不可评审、不可回溯。

### 2.3 值得捡回的精华



| v5.4 设计                                                          | 价值                            | 在本方案的去向                                 |
| ---------------------------------------------------------------- | ----------------------------- | --------------------------------------- |
| `char_matrix`**（char\_id × chapter\_no 章态快照：位置 / 情绪 / 知识 / 物品）** | Writer 只查 N-1 快照，精确省上下文；长篇防漂移 | 投影二期核心表，**且正好承载角色八问动态项**                |
| hooks 债务 / 疲劳 + statistics 聚合                                    | 一条 SQL 替代数百行正则                | 投影一致性 VIEW                              |
| `checkpoints.content_hash`（SHA-256）+ workflow 状态 + lock          | 防跳步、防假完成                      | **不依赖 db**，用 JSON + verify 零依赖实现（§5）    |
| Settler 唯一写库                                                     | 写权限收口                         | 已被 S4 档案员继承                             |
| 只读 seed 知识库（15 表技法）                                              | 静态技法检索                        | 已被 BM25/ZVEC 检索 `library/` 等价覆盖，**不重造** |

### 2.4 结论与三修正



* 方案 B（db 取代 md）已被证伪；方案 C（md/db 双写都可改）必然漂移，否决；**选方案 A（md 单写 SSOT + db 只读派生投影）**。

* 相对 v5.4 的三个关键修正：

1. **Agent 绝不写 db**：v5.4 让 Settler 裸写 SQL 是脆弱根源。本方案 Agent 只写 md，`build_truth_db.py` 机械灌库，Agent 经只读 `truth.py` 取数。

2. **db 放项目内、自包含**：`故事/index/truth.db`（随项目走），不硬编码主目录。

3. **schema 真关系化 + 真约束**：主键唯一 / 外键 / CHECK / 严格列，把 v5.4 没拿到的强约束在 "构建期 schema-on-read 校验 md" 时拿到 ——**md 脏 = build 失败 = 落库失败**。

## 3. 三层存储分工（md / JSON / SQLite）

### 3.1 本质能力对比



| 维度        | md（血肉）       | JSON（关节）         | SQLite（骨骼）                 |
| --------- | ------------ | ---------------- | -------------------------- |
| 本质        | 叙述性半结构化文本    | 结构化纯文本           | 关系型二进制库                    |
| 人读 / 手改   | 最佳           | 可（缩进后）           | 不可（需工具）                    |
| LLM 原生消费  | 原生 Read/Edit | 可解析              | 必须走 CLI                    |
| git diff  | 友好           | 友好（pretty-print） | 不可 diff                    |
| 精确查询 / 聚合 | 弱（要写解析）      | 弱（全量加载）          | 强（SQL / 索引）                |
| 强约束 / 事务  | 无            | 无（靠代码校验）         | 主键 / 外键 / CHECK / 事务       |
| 运行时依赖     | **零**        | **零**            | 需 Python（内置 sqlite3，无第三方包） |
| 生命周期      | 权威源，进 git    | 配置 / 流程态，进 git   | 派生缓存，gitignore、可重建         |
| 写入口       | 人 / S4       | 人 / 流程脚本         | **仅 build 脚本**             |

### 3.2 选型决策判据（按顺序问）



1. 人要逐字读 / 手改，或 LLM 要当 "文章" 消费？→ **md**

2. 配置 / 流程状态、嵌套小数据、要程序可靠读又想保持纯文本零依赖？→ **JSON**

3. 海量同构记录、要按条件查询 / 聚合 / 跨实体强一致？→ **SQLite 只读投影**

两条附加轴：**写入口**（人 / Agent 只写 md、JSON；db 只由脚本写）；**进不进 git**（md/JSON 进、可 diff；db 与全文索引 gitignore、可重建）。

### 3.3 引擎数据 → 载体 全量映射（对齐现有真实文件）



| 数据                                                    | 载体                                                    | 说明                     |
| ----------------------------------------------------- | ----------------------------------------------------- | ---------------------- |
| 正文、细纲、检验 / 变更报告、流程日志                                  | **md**                                                | 叙述，人读、S2 直接消费、git diff |
| 角色卡：核心身份 / 性格底色 / 语言基线 / 硬边界 + **缺点、生活习惯**（八问静态）      | **md**（char\_baseline 投影）                             | 长文本底色，建档一次             |
| 世界观核心规则、地点叙述、技法库、模板                                   | **md**                                                | 知识叙述                   |
| `novel-config.json`（字数 / 视角 / 模块开关）                   | **JSON**                                              | 已是，配置型                 |
| checkpoint（各步 done + output\_ref + **content\_hash**） | **JSON**（§5）                                          | 流程态、程序校验、零依赖           |
| 输入包清单 / 隔离声明（D-214）                                   | **JSON**（§5）                                          | 机器校验 + token 自统计       |
| 角色**当前态**（生死 / 位置 / 情绪 / 已知 / 物品）                     | md SSOT → **characters 投影**                           | 每角色最新一行                |
| **角色 × 章 历史快照**（八问动态项沉淀）                              | 细纲 §6 + CR（md）→ **char\_matrix 投影（二期）**               | 跨章防漂移                  |
| hooks 实例                                              | md SSOT → **hooks 投影**                                | 唯一性 / 债务 / 回收一致性       |
| objects 持有链                                           | md SSOT → **objects 投影**                              | 持有者唯一 / 存在性            |
| timeline 事件                                           | md SSOT → **timeline\_events 投影**                     | 按章 / 时间范围查询            |
| relationships 关系边                                     | md SSOT → **relationships 投影**                        | 双方存在 / 强度域             |
| 地点状态机                                                 | md SSOT → **world\_locations 投影**                     | phase 枚举约束             |
| 章节进度 / 字数 / 五件套齐备                                     | 元数据 md → **chapters 投影**                              | 跳号 / 未落库 / 半成品聚合       |
| 每章摘要 / 变更汇总                                           | chapter\_XXXX + CR（md）→ **chapter\_summaries 投影（二期）** | 滚动窗口 / 跨会话续写           |
| 正文全文检索                                                | BM25/ZVEC 索引（**召回层，非 SQLite**）                        | 相关性召回，已有               |

> 细纲是 "一次性消费 + 归档" 的叙述文档，查询价值低，
>
> **不进投影**
>
> ；滚动窗口仍读 md 细纲（仅冲突链 + 信息释放两节）。

### 3.4 两个 "不要"（v5.4 教训）



1. **不要把 JSON 当字符串塞进 SQLite 的 TEXT 字段**：能枚举 / 要查询 / 要约束的拆成真列或子表；真正不规则的富文本（心理描写、关系备注、规则 bullet、持有链原文）**不进库，只在库里留指回 md 的&#x20;**`source_ref`**&#x20;指针**，需要时回读 md。

2. **不要让同一份数据 md/JSON 双写**：细纲、真相只保留 md 一份，结构化由 build 脚本 schema-on-read 解析，禁止 S1/S4 同时另写一份 JSON 真相。

### 3.5 分层数据流

```
        ▼  （Agent 只读 mode=ro；gitignore；丢了 rebuild；无 Python 降级读 md）
  ┌───────────────────────────────────────────────┐
  │  SQLite 骨骼：characters/char_matrix/hooks/      │
  │   objects/relationships/timeline/world_locations │

```

## 4. 真相不做知识库：三层信任模型与冲突裁决

### 4.1 召回 ≠ 真相



* **知识库 / RAG 解决 "相关性召回"**：语义 top-k，近似、会漏会错、随分片 / 模型漂移、无事务、无唯一约束。

* **真相 SSOT 解决 "事实的权威当前值"**：确定、完备、可枚举、可复现、强一致。

* "林野现在死没死、人在哪" 不能靠 "召回几段最相似的文本投票"—— 向量库会把第 3 章 "在 A 地" 与第 30 章 "在 B 地" 两段矛盾内容都返回，把裁决踢回给最不可靠的环节，正是事故根因。

### 4.2 三层信任模型



| 层        | 载体                      | 回答          | 性质                        | 冲突时权力                 |
| -------- | ----------------------- | ----------- | ------------------------- | --------------------- |
| **权威层**  | md 真相 SSOT              | "现在到底是什么"   | 唯一可写、人改、git、Change Report | **唯一裁决依据**            |
| **一致性层** | truth.db 投影 + verify.py | "有没有违反硬规则"  | 确定性、可复现                   | 硬冲突 FAIL 打回           |
| **召回层**  | BM25 / ZVEC（query.py）   | "以前有没有相关片段" | 近似 top-k                  | **只供线索、WARN、不阻断、不裁决** |

### 4.3 冲突检查（三道，可多方）



1. **事中硬拦（确定性）**：S4 落库 rebuild 时，主键 / 外键 / CHECK / 状态机即时拦截 ——ID 重复、非法状态枚举、持有者不存在、resolved 却无回收章、强度越界 —— 当场 build 失败、可复现，能当门禁。

2. **事后扫描**：verify.py settle/all 跑一致性 VIEW 与既有正则；**语义类**（设定宪法、算术、机械降神、章际衔接）机器不判，落 S3 双视角 Q6/Q7。

3. **召回供线索**：BM25/ZVEC 召回 "疑似矛盾的历史片段" 喂给 S3，**只提示、不阻断**（embedding 比对有假阳 / 假阴、不可复现，不能做 FAIL）。

### 4.4 登记 / 裁决（唯一出口）



* **唯一登记人 = S4 档案员，单点串行写 md**；登记册 = **Change Report（append-only 变更日志，带 evidence\_ids）**。

* **硬冲突不解除，不许登记新状态**（build/settle FAIL，落库中止，沿用 S4 暂存→校验→提交→回滚）。

* **软冲突**（语义 / 解读分歧）由人或编辑裁决，结论**仍回 S4 写进 md 与 Change Report**，形成闭环。

* 检查可以众包（schema /verify/ S3 / 召回），**定稿与登记收口在一个角色、一套文件**。

### 4.5 为什么知识库不能自己检查 / 合并冲突

向量库**没有事务、没有 "事实当前值"、没有唯一约束**：同一事实的多个矛盾版本永久并存，它不知道 "火属性 vs 水属性" 哪个新、哪个对。"自动去重 / 合并" 只对**完全重复的文本块**有效，对**矛盾事实**无效，甚至会把冲突静默搅在一起。**知识库天然无裁决能力，这正是它不能当真相源的原因。**

### 4.6 与现有 query.py（ZVEC）的关系

召回层已存在（`runtime/query.py` + `bm25_fts.py`）。真相文件**可以被索引用于 "找"**，但相关文档必须写明其定位："**召回结果只供线索，不代表事实当前值，不阻断流程**"。事实定稿永远回 md SSOT。投影只读查询 CLI 另行命名 `truth.py`，避让已占用的 `query.py`。

## 5. JSON 层规格（零依赖，建议并入 v1.9.2）

> v5.4 最实用的 checkpoints（content_hash 防跳步 / 防假完成）
>
> **不需要数据库**
>
> ，纯文本 JSON + verify 即可零依赖实现，无 Python 宿主也能肉眼核对。

### 5.1 checkpoint 清单



* 路径建议：`故事/元数据/checkpoint_第XXXX章.json`（与 chapter\_XXXX.md 同目录）。

* 字段（草案）：



```
{
  "chapter_no": 12,
  "mode": "multi",
  "steps": [
    {"step": "S1_outline",  "done": true, "output_ref": "大纲/细纲_第0012章.md", "sha256": "…"},
    {"step": "outline_gate","done": true, "output_ref": "故事/元数据/细纲门_第0012章.md","sha256":"…"},
    {"step": "S2_draft",    "done": true, "output_ref": "正文/第0012章 标题.md",  "sha256": "…"},
    {"step": "S3_review",   "done": true, "output_ref": "故事/元数据/检验报告_第0012章.md","sha256":"…"},
    {"step": "S4_settle",   "done": false, "output_ref": null, "sha256": null}
  ],
  "updated_at": "2026-10-12T20:00:00"
}
```



* 由各阶段流程产出（S1/S3/S4），**verify 校验**：产物文件存在、sha256 与当前文件一致（防 "标了 done 但产物被删 / 被换"）、阶段顺序不可越级。

* 与现有 `故事/日志/第XXXX章.md`（S1-S4 合一叙述日志）**不重复**：md 日志保留给人读的过程叙述；JSON 只放机器可校验的状态 / 哈希。

### 5.2 输入包与隔离声明（D-214 结构化）



* `故事/元数据/输入包_第XXXX章.json`：列明本章 S2 实际输入文件清单 + 各自 sha256 + `isolation`（multi=physical / single=declared）。

* single 模式按 v1.9 口径记 "声明级最小化，非物理隔离"，不冒充物理隔离。

### 5.3 输入包 token 自统计（让成本可实测）



* S4 统计本章输入包字节数，按口径估算 token，写进日志：



```
本章输入包：细纲 3.1KB + 检验报告 2.4KB ≈ 1900 token（UTF-8 中文约 1KB≈300–500 token，随模型校准）
```



* 零依赖（纯字节计数）；跑几章 T1 / 批跑即得 single/multi、各模块、各阶段真实成本，回填模块卡 "高 / 中 / 低"，不再靠拍脑袋。

### 5.4 为什么用 JSON 不用 db

小、嵌套、流程态、需要程序可靠读取又要零 Python 可看；不涉及跨实体查询 / 聚合，上数据库是过度工程。

## 6. SQLite 投影层规格（P2）

### 6.1 定位与边界



* **派生、只读、可重建、gitignore、机器层零 LLM token**。

* 是**事后一致性证明**（落库瞬间 build 校验），**不是事中事务**；写入原子性仍由 S4 四步（暂存→校验→提交→回滚）保证。真・事中事务只有方案 B，已否决。

* 只接管**跨章累积真相实体**的查询与一致性；**正文文本质量门禁（#15 逗号 / #17 重复 / #19 半角 / #26 章末净化 / #30 破折号 / #33 末句雷同）继续留在 verify.py，不进真相库**。

### 6.2 文件位置、开关与依赖



* 路径：`故事/index/truth.db`（与 BM25/ZVEC 索引同目录，该目录**已被 .gitignore 与打包排除**）。

* 开关：`novel-config.json → modules.truth_db`，**默认关**，P2.3 验证成熟后再评估默认开。

* 依赖：需 Python + **内置 sqlite3（无第三方 pip 包）**；无 Python 自动降级为直接读 md 活跃区（§8），流程不阻断、日志标注降级。

* 模块卡 tokens 标注：**低（build / 查询在机器层零 LLM token，精确取数反而省上下文）**。

### 6.3 表结构（真关系化 DDL 草案，对齐现有 md 列）

> 开启连接即 
>
> `PRAGMA foreign_keys = ON;`
>
> 。下列为关键表，字段名与 
>
> `templates/truth/*.md`
>
>  表头一一对应。



```
-- 构建元数据与源文件指纹（新鲜度门禁）
CREATE TABLE source_files(
  path TEXT PRIMARY KEY,        -- 相对项目根的 md 路径
  sha256 TEXT NOT NULL,
  built_at TEXT NOT NULL
);

-- 角色基线（characters.md「基线摘要」，极少变动）
CREATE TABLE char_baseline(
  char_id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  identity TEXT, personality TEXT, speech_baseline TEXT, hard_boundary TEXT,
  source_ref TEXT
);

-- 角色当前态（characters.md「当前状态」）
CREATE TABLE characters(
  char_id TEXT PRIMARY KEY REFERENCES char_baseline(char_id),
  name TEXT NOT NULL,
  mortal_status TEXT NOT NULL
    CHECK (mortal_status IN ('alive','missing','false_dead','true_dead','resurrected')),
  location TEXT, emotion TEXT, knowledge TEXT, inventory TEXT,
  source_chapter INTEGER NOT NULL CHECK (source_chapter >= 0),
  visibility TEXT,
  source_ref TEXT
);

-- 角色×章 历史快照（二期；数据源=细纲§6 + 每章 Change Report 旧→新四字段回放）
CREATE TABLE char_matrix(
  char_id TEXT NOT NULL REFERENCES characters(char_id),
  chapter_no INTEGER NOT NULL CHECK (chapter_no >= 1),
  mortal_status TEXT, location TEXT, emotion TEXT, knowledge TEXT, inventory TEXT,
  source_ref TEXT,
  PRIMARY KEY (char_id, chapter_no)
);

-- 伏笔（hooks.md）
CREATE TABLE hooks(
  hook_id TEXT PRIMARY KEY,
  hook_type TEXT NOT NULL CHECK (hook_type IN ('mystery','emotion','chekhov','identity','other')),
  content TEXT NOT NULL,
  plant_chapter INTEGER,
  planned_reap_chapter INTEGER,      -- 只能填数值章号；“卷X后期(约NN)”文本归 NULL 并 WARN
  actual_reap_chapter INTEGER,
  progress TEXT CHECK (progress IN ('pending','partial','due')),
  next_resolved_at INTEGER,
  status TEXT NOT NULL CHECK (status IN ('active','resolved','abandoned','pending','expired','stale')),
  visibility TEXT, source_ref TEXT,
  CHECK (actual_reap_chapter IS NULL OR
         (plant_chapter IS NOT NULL AND actual_reap_chapter >= plant_chapter)),
  CHECK (status <> 'resolved' OR actual_reap_chapter IS NOT NULL)
);

-- 物品（objects.md）
CREATE TABLE objects(
  obj_id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('owned','lost','destroyed','sealed','transferred')),
  holder TEXT REFERENCES characters(char_id),   -- 持有者必须存在；解析出多持有者→冲突
  chain_text TEXT,                               -- 持有链历史原文（一期不拆）
  criticality TEXT CHECK (criticality IN ('plot-critical','普通')),
  source_chapter INTEGER, visibility TEXT, note TEXT, source_ref TEXT
);

-- 关系（relationships.md 关系矩阵）
CREATE TABLE relationships(
  char_a TEXT NOT NULL REFERENCES characters(char_id),
  char_b TEXT NOT NULL REFERENCES characters(char_id),
  rel_type TEXT,
  intensity INTEGER CHECK (intensity BETWEEN 1 AND 10),
  history TEXT,
  PRIMARY KEY (char_a, char_b)
);

-- 时间线（timeline.md）
CREATE TABLE timeline_events(
  chapter_no INTEGER NOT NULL,
  seq INTEGER NOT NULL DEFAULT 0,
  in_story_time TEXT, event TEXT NOT NULL, entities TEXT,
  visibility TEXT CHECK (visibility IN ('reader_known','author_truth')),
  source_ref TEXT,
  PRIMARY KEY (chapter_no, seq)
);

-- 地点状态机（world.md）
CREATE TABLE world_locations(
  location TEXT PRIMARY KEY,
  phase TEXT NOT NULL CHECK (phase IN ('intact','damaged','destroyed','abandoned','rebuilt','transformed')),
  transition_chapter TEXT, source_chapter INTEGER, visibility TEXT,
  narrative_resources TEXT, source_ref TEXT
);

-- 章节进度（元数据 index.md + chapter_XXXX.md）
CREATE TABLE chapters(
  chapter_no INTEGER PRIMARY KEY,
  title TEXT,
  status TEXT NOT NULL CHECK (status IN ('outline_only','drafted','in_review','archived')),
  word_count INTEGER,
  has_brief INTEGER NOT NULL DEFAULT 0 CHECK (has_brief IN (0,1)),
  has_change_report INTEGER NOT NULL DEFAULT 0 CHECK (has_change_report IN (0,1)),
  has_review INTEGER NOT NULL DEFAULT 0 CHECK (has_review IN (0,1)),
  source_ref TEXT
);

-- 每章摘要（二期；chapter_XXXX.md change_summary + CR）
CREATE TABLE chapter_summaries(
  chapter_no INTEGER PRIMARY KEY REFERENCES chapters(chapter_no),
  core_event TEXT, character_changes TEXT, hooks_planted TEXT,
  hooks_reaped TEXT, world_changes TEXT, source_ref TEXT
);
```

**一致性 VIEW（把 verify 真相 / 进度类正则迁到确定性 SQL）**，示例：



```
CREATE VIEW v_hook_debt AS            -- 移植 #28：active 且非 partial 的超期伏笔
  SELECT hook_id, hook_type, plant_chapter, planned_reap_chapter, status
  FROM hooks WHERE status='active' AND COALESCE(progress,'pending')<>'partial'
    AND ( (planned_reap_chapter IS NOT NULL AND planned_reap_chapter < :cur) );

CREATE VIEW v_object_bad_holder AS    -- 持有者不存在 / 多持有者（解析期标记）
  SELECT obj_id, name, holder FROM objects
  WHERE criticality='plot-critical' AND (holder IS NULL OR holder <> '');  -- 多持由解析器置错误标记

CREATE VIEW v_archived_missing_cr AS -- 唐末第 3 章类：已归档却缺 Change Report
  SELECT chapter_no FROM chapters WHERE status='archived' AND has_change_report=0;

CREATE VIEW v_chapter_gap AS          -- 移植 #32：跳号 / 有正文未归档
  SELECT c.chapter_no FROM chapters c
  WHERE c.status<>'archived' AND c.word_count IS NOT NULL;

CREATE VIEW v_char_matrix_gap AS      -- 二期：章态快照断链（缺 CR 的章节会暴露）
  SELECT ch.char_id, g.chapter_no FROM char_matrix g
  RIGHT JOIN chapters ch ON ch.status='archived';  -- 具体缺口由 build 差分计算
```

> 正文文本类检测（死者是否在晚章正文 "出现"、口癖密度、重复句、末句雷同）仍由 verify.py 处理；投影只提供 "该角色 true_dead 于第 N 章" 这类权威事实供 verify/S3 比对。

### 6.4 待固化的口径（P2.1 前置小清理）



1. **visibility 各表值域不统一**：characters/objects 为 `public/角色名`，timeline 为 `reader_known/author_truth`。一期投影按各表原值存储、不强行 CHECK；P2.1 先统一值域规范再加强约束。

2. **planned\_reap\_chapter 文本化**："卷 X 后期（约 NNNN）" 非整数。投影要求可数值章号；文本型计划在 build 时归 NULL 并 WARN，债务检测对其跳过（沿用 verify #28 口径）。

3. **持有链 "谁→谁→谁"**：一期保留 `chain_text` 原文 + 只结构化当前 holder；object\_chain 边表留待二期。

4. **自由文本列**（关系备注、规则 bullet、事件叙述、可用叙事资源）：一期不拆，存原文或 source\_ref。

### 6.5 build\_truth\_db.py 规格（唯一写库者）



* **全量、幂等、零第三方依赖**（sqlite3 + 复用 verify.py 的 md 表格解析器，抽为公共函数）。

* 流程：解析 6 真相 md + 元数据 index/chapter\_XXXX + Change Report → 在临时库建表灌数据并启用全部约束 → 全部通过后 `os.replace` **原子替换** truth.db（失败不留半成品库）。

* 写 `source_files.sha256`（6 真相 + 元数据）供新鲜度比对。

* md 脏（重复主键、外键悬空、非法枚举、resolved 缺章、强度越界、缺 CR 等）→ **非零退出 + 错误清单（文件 / 表 / 行 / 原因）**，对应 S4 落库 FAIL。

* 输出每张表行数与 WARN 列表；规模预期：数千章秒级完成，故不做脆弱的增量更新。

### 6.6 truth.py 只读查询 CLI 规格



* 以 `sqlite3.connect("file:...?mode=ro", uri=True)` **只读打开**，任何写入直接报错。

* 子命令（草案）：


  * `char <id> [--chapter N]`：当前态或第 N 章快照

  * `due --chapter N`：本章应推进 / 回收的 hooks（+ focal goals）

  * `object <id>` / `holders`；`rel <id>`；`timeline [--from A --to B]`

  * `chapter N`：摘要 + 本章变更

  * `doctor`：跑全部一致性 VIEW，输出 FAIL/WARN 清单

  * `stats`：字数 / 状态趋势

* 全局 `--max-chars`（默认回灌上限）、`--format compact`；**禁止全量 dump**，只回灌本章所需行。

* 库不存在 / 已过期：提示先 build 或降级读 md，不致命报错。

### 6.7 接入点



* **S4 提交后**：与 verify settle 同环节跑 `build_truth_db.py`（全量 rebuild）。

* **verify settle 新增 "投影新鲜度" 门禁**：db 存在但 `source_files.sha256` 与当前 md 不符 → FAIL"投影过期，请 rebuild"；db 不存在且 `truth_db=false` → 跳过。

* **S1 取数切换（P2.3）**：启用投影后，S1 用 truth.py 精确取数替代整读 characters/hooks/objects/timeline；仍读 md 的分卷 / 章节大纲、上章细纲 / 检验报告、滚动窗口历史细纲。

* **S2 不接真相层**：讲述者物理隔离不变，所需知识边界仍由 S1 压缩进细纲 §6 透传。

### 6.8 降级



* 无 Python / 未启用 truth\_db：整个投影层跳过，S1 直接读 md **活跃区**（§8，分区后读取量受控），日志记 "真相投影降级 = 直接读 md"，门禁与产物不减。

### 6.9 char\_matrix 历史快照可行性（二期）



* Change Report 第一节已固定 "位置 / 状态情绪 / 已知信息 / 携带物品" 的**旧→新**四字段，叠加基线可**回放重建**每章每角色快照。

* **缺某章 CR = 快照断链**（唐末第 3 章即如此）：build 应报 `char_matrix gap @chapter N`，按门禁级别 WARN（历史）或 FAIL（当前章）。

* 历史 CR 不规范的老书：**从启用投影的章节起向前累积，不强行回填**，缺口明确标注。

## 8. md 真相活跃 / 归档分区（v1.9.2，零依赖，投影前置）



* SQLite 投影**不免除 md 自身膨胀**；分区是投影的前置，且独立有用。

* **活跃区**（S1 每章必读，体量有上界）：当前卷相关、在场 / 存活角色当前态、`active`/`due` 伏笔、当前地点状态、近窗 timeline、focal/suppressed 目标。

* **归档区**（不进常驻上下文，按需检索）：resolved/abandoned 伏笔、离场 / 死亡角色、历史地点、旧卷 timeline 与章节摘要。

* 分区后**仍是 md**（人可读可改、git 可 diff）；投影 build 同时覆盖活跃 + 归档，查询靠 truth.py/ BM25 / ZVEC。

* 配合滚动窗口 N-5\~N（只读历史细纲 "冲突链 + 信息释放" 两节）。

## 9. Token 账

**标尺：只有进 LLM 上下文的文本花 token；Python 的 build/verify/hash/ 查询花时间不花 token。**



| 新增项                       | 类型       | 增减    | 数量级（估算，待实测）                       |
| ------------------------- | -------- | ----- | --------------------------------- |
| 八问静态（习惯 / 缺点 / 能力）        | 一次建档     | 微增    | 每角色约 100–200 token，后摊薄≈0          |
| 八问动态（细纲 §6）               | 每章       | 增     | 约 300–800 token / 章（仅 POV + 关键角色） |
| 自主性 S1 自检 + S3 Q8         | 每章       | 微增    | 检验报告多几百～1k token                  |
| md 活跃 / 归档分区              | 每章 S1 读  | **省** | 章数越多越省，必读量有上界                     |
| JSON checkpoint/hash/ 输入包 | 每章输出     | 微增    | 约 200–400 token / 章；hash 零 token  |
| truth.db build            | 机器       | **0** | 秒级                                |
| truth.py 精确取数             | 每章 S1/S3 | **省** | 回灌几百～1k，替代读整文件数千～数万               |
| S3 加严（双视角 / Q6Q7）         | 每章       | 增     | 中（数千 token / 章，可分档）               |
| 物理隔离 S2 只读细纲              | 每章 S2    | **省** | S2 窗口不再带规则 / 状态 / 技法库             |



* **前几十章（真相小）：净微增**，买质量与防崩；**几百章以上：净大省**，把每章必读钉成常量。

* **最大隐藏节省是返工**：重写一章 = 全章正文 + S1-S4 全套（上万 token），结构化前置用几百 token 省上万 token 返工。

* 控量开关：机器结论只回灌几行；八问仅 POV + 关键角色；truth.py `--max-chars` 禁全量；S3 分档；单一事实只透传一次；db / 索引永不进上下文。

* 成本以 §5.3 输入包自统计实测为准，回填模块卡高 / 中 / 低与本估算偏差。

## 11. 验收（用已知答案做 ground truth）



1. **已知脏数据必须被抓出**：对唐末 / 星尘跑 build + `truth.py doctor`，至少报出 ——h\_007 重复、第 3 章缺 CR / 未落库（v\_archived\_missing\_cr）、timeline 滞后、物品异常持有、章节进度与正文不符；逐条对照已知事故清单。

2. **干净合成项目**：build 通过；连续两次 rebuild 的 truth.db 内容与 source hash 一致（幂等）；临时库失败不覆盖旧库（原子性）；30 章全量秒级。

3. **只读与限量**：truth.py 以 mode=ro 写入即报错；`--max-chars` 生效，无法全量 dump。

4. **新鲜度门禁**：改一个真相 md 后不 rebuild → settle FAIL；rebuild 后 PASS。

5. **降级演练**：关闭 truth\_db / 无 Python，全流程改读 md 活跃区，不阻断、日志标注降级、产物不减。

6. **工程门禁**：`py_compile` 通过；不新增第三方依赖；doc\_sync check 通过。

## 12. 风险与诚实边界



1. build 仍需解析 md（schema-on-read），只是把解析脆弱性**收敛到一个脚本**，是改善而非银弹；自由文本列一期不硬关系化。

2. 投影是**事后一致性证明，非事中事务**；写入瞬间原子性仍靠 S4 四步。

3. 投影**不解决 md 膨胀**，5000 章仍依赖活跃 / 归档分区（§8 先行）。

4. char\_matrix 老书历史不规范则从启用章累积，不强行回填。

5. **语义冲突（设定宪法、算术、机械降神、章际衔接）机器仍不判**，坚持落 S3，不假装可自动裁决。

6. truth\_db 模块卡必须向用户讲清依赖（需 Python、默认关、无 Python 自动降级）与成本（机器层零 token、取数省上下文）。
