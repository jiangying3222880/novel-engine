## 一、Skill 标准如何确认

### 1.1 权威来源（两处，已核对）

- **Agent Skills Specification**（跨平台通用规范）
- **WorkBuddy skill-creator**（本机 `D:\Program Files\WorkBuddy\...\skills\skill-creator\SKILL.md`）

### 1.2 硬标准（机器可验）

| 项 | 要求 | 你的现状 |
|---|---|---|
| 目录名 == `name` | 必须一致 | ✅ `novel-engine` |
| `name` 格式 | 1-64 字符，仅 `[a-z0-9-]`，不首尾连字符，无 `--` | ✅ |
| `description` | 1-1024 字符，非空，无 XML 标签 | ✅ 合规 |
| `description` 内容 | **必须同时说明"做什么"+"何时用"，含触发关键词** | ❌ **不合格** |
| frontmatter | YAML 合法（Tab 会静默解析失败） | ✅ |
| `agent_created: true` | WorkBuddy 要求，供 `skill_manage` 管理 | ❌ **缺失** |

### 1.3 软标准（渐进式披露，官方强烈建议）

官方原文三级加载：

| 层级 | 内容 | 预算 |
|---|---|---|
| 元数据 | name + description，启动时全部加载 | ~100 token |
| 指令 | SKILL.md 正文，激活时整份加载 | **< 500 行 / < 5000 token** |
| 资源 | scripts/ references/ assets/，**按需**加载 | 不限 |

**你的现状**：
- SKILL.md **172 行** ✅（达标，< 500）
- 但 **17135 字节** ≈ 约 5700 汉字 ≈ **8000~11000 token** ❌ **超建议值约 2 倍**

> 中文 1 字约 1.5-2 token，红线比"17KB"这个字节数更紧。这就是你一直感觉"17KB 红线"别扭的原因——
> 真正的约束是 token 不是字节。

### 1.4 官方校验器有多弱（重要）

`skill-creator/scripts/quick_validate.py` 全文仅 64 行，只查 5 项：
frontmatter 格式 / name 存在 / description 存在 / name 命名 / description 无 XML 标签。

**它不查**：体量、description 是否含"何时用"、目录名匹配、references 断链、渐进式披露。

实测结果：
```
$ python quick_validate.py novel-engine
Skill is valid!
```

**"通过"只是最低门槛，不是合格。** 这跟你技能里"工具残留检查只查有没有标、不查标得对不对"是同一类假绿灯。

### 1.5 结论：标准要靠自建校验器确认

建议新增 `runtime/skill_lint.py`，在官方 5 项之上追加：
- description 触发词检查（必须含"当…时/用于/触发"类信号 + 领域关键词）
- SKILL.md token 估算（中文按 1.7 token/字，红线 5000）
- 目录名 == name
- references/ 内被 SKILL.md 引用的文件是否存在（断链）
- `agent_created` 存在性

并接进 pre-commit（与 doc_sync 并列）。

## 二、意图 / 全部功能如何转成 Skill

### 2.1 切分原则

**按"一次会话只干一件事"切，不按文档类型切。**
验收标准：用户只想写章节时，需要加载的子技能 ≤ 2 个。

### 2.2 意图 → 子技能映射

| 用户意图（自然说法） | 子技能 | 主要文件 |
|---|---|---|
| 我要开本书 / 建项目 / 初始化 | `ne-setup` | project-setup.md |
| 写大纲 / 排细纲 / 这章写什么 | `ne-outline` | 细纲模板 / narrative-kernel / target-focus |
| 写正文 / 续写 / 这一章 | `ne-write` | workflow-detail / writing-guide / execution-modes |
| 检查一下 / 有 AI 味吗 / 打回 | `ne-review` | self-review / anti-ai* / 检验报告模板 |
| 存盘 / 更新状态 / 伏笔 / 接着上次写 | `ne-memory` | hooks-and-memory / session-start / retrieval |
| 写个短篇 / 一万字完结 | `ne-short` | short-story* |
| 找个梗 / 技法 / 类型套路 | `ne-library` | library/ 158 文件 |
| 跑门禁 / 校验 / 打包 / 部署 | `ne-tools` | runtime/*.py |
| 意图不明 | `ne`（路由） | 路由表 + 降级 |

### 2.3 转化时的三条纪律

1. **每个 SKILL.md 自包含**：共享铁律几百字复制到各子技能头部，不靠跨目录引用
   （豆包/网页端读不到其他技能目录）
2. **description 必须重写**：每个子技能单独写"做什么 + 何时用 + 触发词"，
   否则 AI 根本不会在对应场景调用它
3. **大素材单列**：`library/` 158 文件整体归 `ne-library`，其余技能按路径引用，不做 8 份拷贝

## 三、在其他智能体下的运行情况

### 3.1 平台能力矩阵

| 能力 | Claude Code | Codex | OpenCode | WorkBuddy | 豆包/网页版 |
|---|---|---|---|---|---|
| 基础 SKILL.md（name/description） | ✅ | ✅ | ✅ | ✅ | ⚠️ 仅当提示词 |
| 扩展字段（14 项） | ✅ 全 | 部分 | 部分 | 部分 | ❌ |
| **子技能路由** | ✅ `/skill` | ✅ `$skill` | ✅ `/skill` | ✅ | ❌ |
| **`context: fork` 物理隔离** | ✅ | ❌ | ✅（agents/*.md） | 未实测 | ❌ |
| **hooks 硬门禁** | ✅ | 部分 | ✅ | 未实测 | ❌ |
| 脚本执行 | ✅ | ✅ | ✅ | ✅ | ❌ |
| 自定义 agent | `.claude/agents/` | `.codex/agents/*.toml` | `.opencode/agents/*.md` | 子 agent | ❌ |

### 3.2 oh-story 的跨平台代价（实测）

它在 `story-setup/references/` 下为每个平台**各写一套** agent 定义：

```
codex/agents/    7 个 .toml   + AGENTS.md.tmpl
opencode/agents/ 7 个 .md     + AGENTS.md.tmpl
openclaw/        AGENTS.md.tmpl
```

**7 个 agent × 多平台 = 几十个文件，上游一改全要同步。** 这就是"真 multi-agent"的维护成本。

### 3.3 对你意味着什么

- **能跨平台跑的**：你攒的中文人味方法论（anti-ai、憋压引擎、声音包、技法库）——纯文本，
  在豆包里照样生效。这是你的护城河，与载体无关。
- **只有 Claude Code / OpenCode 能享受的**：真物理隔离、hooks 硬门禁、自动子 agent 调度。
- **豆包/网页版的现实**：没有子技能路由、没有 hooks、不能跑 Python。
  → **必须走 single 降级模式**（三条硬指令模拟隔离），且门禁要能降级为手动清单。

**结论**：不要为"在所有平台都完整"设计。核心方法论全平台通用，
硬机制（隔离/门禁）按平台能力分档，低能力平台降级不硬失败（你现有 execution-modes.md 的
multi/single 设计方向是对的，保留）。

## 四、开关机制：已经有了，但粒度不够

### 4.1 现状（实测，不是推测）

**`novel-config.json → modules` 这套开关 v1.8 就存在，而且是 SSOT 级设计：**

```json
"modules": {
  "short_story": true, "chat_outsource": true, "pool_teardown": true,
  "obsidian_overview": false, "zvec": false
}
```

配套三件套齐全：
- `verify.py` 检查项 9a：`config.modules 字段存在且合法（模块 SSOT）`
- `references/module-registry.md`：模块注册表（M-001~M-005，含触发条件）
- `project-setup.md:155`：初始化 Step 5.6 **逐项向用户确认**开/关，每本书重新确认不跨项目继承

**所以第 4 问的答案是：不用新建，已有且设计正确。**

### 4.2 真正缺的是粒度

现有 5 个开关都是"边缘功能"，**你嫌重的那些主流程环节一个都关不掉**：

| 环节 | 能否关 | 现状 |
|---|---|---|
| 细纲门（硬性结构检查） | ❌ 关不掉 | 每章必过 |
| S3 检验报告 | ❌ 关不掉 | 每章必过 |
| 技法库加载 | ❌ 关不掉 | 每章必读 |
| 滚动窗口 N-5~N | ❌ 关不掉 | 每章必读 |
| 门禁严格度 | ❌ 关不掉 | FAIL 一律阻断 |

### 4.3 建议：加一层"流程级开关"

在 `modules` 同级加 `pipeline`，让**模式可切换**：

```json
"pipeline": {
  "mode": "light",            // light | standard | strict
  "outline_gate": false,      // 细纲门：light 下关闭
  "review_gate": false,       // S3 检验报告：light 下关闭
  "technique_load": "on_demand",  // always | on_demand | off
  "rolling_window": 3,        // 读前 N 章；light 下 3，standard 5
  "gate_strictness": "warn"   // block | warn：light 下误报只警告不阻断
}
```

**直接治你的痛点"流程太重"**：light 模式下写章 = 细纲 → 正文 → 落库，2 次调用，
细纲门和检验报告都不跑，门禁误报也从"阻断"降为"警告"（顺带解决上次那个
「我用了技巧」误报卡死流程的问题）。

配套改动：
- `project-setup.md` Step 5.6 增加"流程模式"选择（轻/标准/严格）
- `verify.py` 读 `pipeline.gate_strictness`，warn 模式下列为 WARN 不阻断
- `execution-modes.md` 增加 light 模式路径

### 4.4 平台侧开关（与项目开关互补）

Claude Code 有官方字段可用：
- `disable-model-invocation: true` → 禁止 AI 自动加载，只能手动 `/name` 触发
- `user-invocable: false` → 从 `/` 菜单隐藏，但保留为背景知识
- `paths: "正文/*.md"` → 只在匹配文件时自动激活

这些适合控制**哪些子技能在哪些场景出现**，与项目内的 `pipeline` 是两层，不冲突。

## 五、可选功能怎么安排（短篇 / 叙事总览 / 多角色 / 网页外包）

### 5.1 判别标准（一句话）

**有没有独立的「输入 → 处理 → 产出」闭环？**
有闭环 = 独立子技能；只是换条路走 = 模式分支；只是查资料 = 素材；依赖外部工具 = 开关。

### 5.2 四样东西分别是什么性质（实测）

| 你提的 | 实际形态 | 性质 | 归属 |
|---|---|---|---|
| **短篇** | `short-story.md` 16KB + `short-story-engines.md` 12KB + 短篇模板 3.9KB，共 32KB；有自己的憋压三段式细纲、文梗引擎库、且 v1.9 已规定"短篇也走细纲门" | **完整独立流水线** | ✅ **独立子技能 `ne-short`** |
| **网页外包** | `chat-outsource.md` 5.9KB（M-002）。原话："技能负责规划与治理，写作外包给任意网页 chat，写完拿回继续自检→去AI味→落库" | **执行通道**，不改变"写什么"，只改变"谁来写" | ❌ 非子技能 → `ne-write` 的模式分支 + 开关 |
| **叙事总览** | 无独立文档，散见于 8 个文件（README / hooks-and-memory / module-registry / 说明书 / project-setup / workflow-detail / routes / selftest_gates.py）；依赖用户装 Obsidian | **外部工具集成**，是 S4 落库的副产物 | ❌ 非子技能 → 保留开关 `obsidian_overview` |
| **多角色** | ⚠️ **2026-10-15 更正**：主人指的是**写作时的身份切换**（作者 / 讲述者 / 编剧 / 编辑 / 读者），**不是**群像素材。<br>它由 `references/identity-routing.md`(6.5K) + `library/identities/`(5 档案) + 项目级 `配置/身份/*.md` 构成，贯穿 S1-S4 每一个环节 | **横切内核，不是子技能** | ❌ 非子技能 → **抽为 `身份路由` 独立 L2 文件，被子技能按需引用**（见 §五.1） |

### 5.3.1 多角色（身份路由）—— 横切内核，不是子技能

> **2026-10-15 更正**：此前误把"多角色"理解为群像/多人物写作素材，实为**写作时的身份切换机制**。两者都要保留，性质完全不同：
> 群像是"写什么"，身份路由是"谁在写"。

**判别为什么它不是子技能**：它没有独立的输入→产出闭环。你不会说"启动多角色"，
你只会说"用讲述者的身份写这一章"。它像电压——每个环节都要用，但自己不产出东西。

**关键设计：把它拆成两个正交的轴**（不要在一份文件里混着写）

| 轴 | 回答什么 | 取值 | 谁定义 | 机器可校验 |
|----|---------|------|--------|-----------|
| **Lane（环节）** | 这一步做什么 | S1 骨架 / S2 血肉 / S3 检验 / S4 落库 | `workflow-detail.md`、`execution-modes.md` | ✅ 产物文件名 + 门禁 |
| **Voice（视角）** | 以谁的嘴和眼睛做 | 作者 / 编剧 / **讲述者** / 编辑 / 读者 / 档案员 | `identity-routing.md` + `library/identities/` | ❌ 靠档案 + 强制问答 |

一个 Lane 只有一个主 Voice；一个 Voice 可跨多个 Lane（作者贯穿立项与 S4）。

**2026-10-15 实测发现的三处硬伤（均已修）**

| # | 问题 | 证据 | 修法 |
|---|---|---|---|
| 1 | **`讲述者` 没有身份档案** | 全技能 54 处提及"讲述者"，但 `library/identities/` 下只有 作者/编剧/编辑/读者 四份 | 新建 `讲述者.md`(4.5K)，含声音样本区 + 动笔四问 + single 自锚三问 |
| 2 | **编号没跟上 S1-S4 迁移** | `identity-routing.md` 仍用废弃的 ⓪①②③④⑤ 六段；而 `workflow-detail.md` 早已是 S1-S4 | 路由表改为 S1-S4；删除已废弃的「④润色」（`workflow-detail.md:195` 已明确定案） |
| 3 | **同一环节两种叫法** | S2 写作在旧表里是「作者+读者」，在 `execution-modes.md` 里是「讲述者」 | 统一定稿：**作者不执笔**。情节编剧定，文字讲述者出，拍板作者做 |

连带发现并已修的扩散污染：`templates/log-template.md`（**每章都要填**，却对着已删除的 ④润色 记录）、
`library/packaging.md`、`references/hooks-and-memory.md:169`（仍写"5 阶段合一"）。

**为什么这直接关联你的头号痛点**：证物链是
`讲述者无档案 → S2 只能"只读细纲" → 声音随技法库一起被隔离 → D-11「物理隔离把文体声音也挡掉了」`。
所以 v1.9.2 的"声音包"不是从零造——**载体就是 `讲述者.md` 的 §五 声音样本区**，且必须是项目级覆盖
（技能级给不出你的声音，这是设计必然，不是漏填）。**注意：切勿用"让讲述者多读点文件"来补声音，那会毁掉隔离本身。**
