## 项目目录命名规范（统一中文 · v1.4 修正）

**原则：项目（每本书）目录内一律中文命名，禁止中英文混用。** 目录是给作者看的，中文便于 Obsidian/本地管理。例外仅限：程序/检索读取的**固定协议文件**（novel-config.json、chapter_XXXX.md、characters.md 等）与**机器产物内部文件**（索引二进制），属内部契约，不参与命名规范。

| 英文旧目录 | 中文新目录 | 说明 |
|-----------|-----------|------|
| `story/truth/` | `故事/真相/` | 6 个状态文件（characters/world/hooks/relationships/objects/timeline） |
| `story/meta/` | `故事/元数据/` | 章节元数据 + index.md（进度唯一真相源） |
| `story/logs/` | `故事/日志/` | 每章流程日志 |
| `story/index/` | `故事/索引/` | 检索索引（机器产物，内部文件名保留英文） |
| `config/identity/` | `配置/身份/` | 项目级身份档案 |
| `pools/` | `素材池/` | 素材池（author_dna/planner/reference 等） |
| `正文/ 大纲/ 设定/ 叙事总览/` | 不变 | 已是中文 |

> 协议文件名（novel-config.json / chapter_XXXX.md / characters.md 等）被检索与自检代码读取，**保持英文文件名**但放中文目录；不属"中英混用"，是固定契约。

## Obsidian 双链规范（自动链接 + 真相隔离 · v1.4 修正）

### 双链隔离原则（最高优先级 · 防止机器不可读）

**数据层（`故事/真相/` 6 个文件 + `故事/元数据/` 索引）是机器数据源**：被检索（BM25/ZVEC）、字段解析、阶段①②③④⑤ 读取。**禁止**在其中出现 Obsidian 双链 `[[ ]]`、叙述性文字或任何非表格内容——一旦污染，字段解析错乱、检索词项被 `[[` 污染，机器不可读。

> 判断标准：数据层（truth + meta）文件里出现 `[[` = 严重缺陷。双链只允许存在于展示层（`叙事总览/`）。

### 自动链接规则（展示层生成时自动建立）

总览（`叙事总览/`）是 Obsidian 纯展示层，生成/落库联动更新时**自动把数据源中的实体转为有效双链**：

| 实体 | 自动链接目标 | 规则 |
|------|-------------|------|
| 角色 | `[[角色名]]` → `叙事总览/角色卡/角色名.md` | 出场角色自动生成角色卡（单向源自 characters.md） |
| 章节 | `[[第000X章 标题]]` → `正文/第000X章 标题.md` | **必须用 body_filename_template 规范名（4位章号）**，与正文文件名精确一致 |
| 概念/地点 | `[[概念名]]` | 可指向总览内锚点或单独笔记 |

> 章节链接常见错误：模板曾写 `[[第1章 标题]]`，与命名规范 `第000X章` 不一致导致链接悬空。**自动链接必须以实际文件名（4位章号）为准。**

### 角色卡机制

- 位置：`叙事总览/角色卡/角色名.md`（Obsidian 原子笔记，展示层）
- 字段：身份 / 目标 / 困境 / 声线 / 当前状态 / 与主角关系（单向源自 characters.md + 设定/角色声线.md）
- 维护：落库联动生成/更新，**不写回真相文件**

### 真相文件机器可读检查（落库/自检强制）

- `故事/真相/` 6 文件扫描 `[[`：出现即判缺陷，必须回滚为纯表格
- 检索 build 前自动校验：真相文件含双链则 build 失败并提示

## 入口 A：从零创建（对话驱动）

通过对话逐步建立项目文件。每步完成后确认再进下一步。

### Step 1：作品基础信息

向用户提问以下内容（用户回答后整理为 novel-config.json）：

1. **书名**：暂定也行
2. **题材**：科幻/玄幻/都市/末日/历史/其他
3. **叙述视角**：第三人称限知 / 第一人称 / 全知 / 多POV
4. **每章目标字数**：先从你已给的设定/材料中提取（如"每章6000-8000字"）；若材料未提到字数 → **必须提问**（2000/3000/4000/6000/8000/其他），禁止静默默认。用户给区间 → target 取中点；给单值 → 直接用。config 只存 `target_word_count` 单值，验收按 ±15%
5. **基调**：冷峻紧凑 / 轻松幽默 / 热血燃向 / 阴暗压抑 / 其他
6. **预计总章数**：心里有数就填，没有就留空

完成后从 `templates/novel-config.json` 生成项目配置。

### Step 2：世界观与核心设定

向用户提问引导（不要一次问太多，分轮对话）：

1. **故事发生在什么地方？** → 提取地理/社会环境
2. **核心矛盾是什么？** → 提取主线冲突（人vs人/人vs环境/人vs自我）
3. **有没有特殊设定？** → 提取力量体系/科技层级/社会规则
4. **时间跨度多大？** → 提取故事时间线（几天/几年/几代人）

用户回答后，Agent 整理为结构化文档：`设定/世界观.md`

### Step 3：角色建立

对每个主要角色（建议先建3-5个核心角色），通过对话获取：

1. **名字和身份**：谁？干什么的？
2. **核心性格**：用3个词形容
3. **说话方式**：话多还是话少？用词偏文还是偏俗？有没有口头禅？
4. **不会做的事**：这个角色绝对不会怎样？（硬边界）
5. **压力下怎么变**：紧张时说话会变成什么样？

按 `templates/voice-profile-template.md` 格式整理为：`设定/角色声线.md`

### Step 4：大纲搭建

分两级建立：

**卷纲**（先建）：`大纲/卷纲.md`

向用户提问：
1. 这本书分几卷？
2. 每卷的核心事件和情绪走向是什么？

**细纲**（逐章建，至少先建前3章）：
- `大纲/细纲_第0001章.md`
- `大纲/细纲_第0002章.md`
- `大纲/细纲_第0003章.md`

### Step 5：初始化状态与元数据文件

**5a. 状态文件（从 `templates/truth/` 复制 6 个模板到项目 `故事/真相/`）：**
- `characters.md` — 角色基线摘要 + 初始状态
- `world.md` — 核心规则摘要 + 初始时间/地点
- `hooks.md` — 空表（含推进状态/下一回收点两列，G 定稿）
- `relationships.md` — 初始关系矩阵
- `objects.md` — 物品状态（关键道具持有链）
- `timeline.md` — 时间线（当前故事时间锚点）

> 关键原则：基线摘要 = 完整设定的"压缩版"，只保留最核心的信息（控制在 2KB 以内）。完整档案仍在 `设定/` 目录下，按需读取。

**5b. 元数据骨架（功能三/四/五）：**
- `故事/元数据/index.md` — 从 `templates/meta/index.md` 初始化（进度唯一真相源）
- `故事/元数据/chapter_0001.md` — 从 `templates/meta/chapter_XXXX.md` 初始化（第1章元数据）
- `故事/日志/` — 每章 1 个流程日志文件（`templates/log-template.md`）
- `配置/身份/` — 作者/编剧/编辑/读者 项目级覆盖（技能级基线在 `library/identities/`，项目级存在则优先）
- `叙事总览.md`（根 MOC 入口）+ `叙事总览/` — 从 `templates/narrative/` 复制 6 个骨架（00_作品总览/01_角色总览/02_世界观总览/03_伏笔追踪总览/04_章节地图/05_关系网）到项目 `叙事总览/`，并按项目已有数据填充关键内容（Obsidian 纯展示层，功能五）。**只建空目录不复制骨架 = 缺陷**（曾导致叙事总览为空）
### Step 5.5：初始化检索索引（默认 BM25+FTS，零依赖）

**默认启用 L1 BM25+FTS**（`runtime/bm25_fts.py`，仅依赖 jieba 分词，无需安装 zvec SDK）：

```
python runtime/bm25_fts.py build --root <项目根>
```

- 索引产物：`故事/索引/bm25/index.json`（truth + meta + 正文分块）
- **检索层说明（告知用户）**：BM25+FTS=词法精确命中（专名检索）；ZVEC=词法+语义混合（可语义召回，需另装 zvec SDK）。两者都有防剧透+知情权过滤。写作期 L1 已够用；要语义检索再把 `runtime/config.yaml` 的 `retrieval.mode` 切到 `zvec`。
- 每次落库（阶段⑤）后重建：`python runtime/bm25_fts.py build --root <项目根>`

### Step 6：对标书拆解（可选但强烈推荐）

> **池子是 Agent 自动拆解出来的，不是手动建出来的。空池子没有价值。**
>
> **拆解是 Agent 的工作，不是用户的工作。** 用户只需提供对标书（书名/文本文件），Agent 负责读取、分析、判断、入池。
>
> **详细拆解方法论**：见 `templates/pools/拆解方法论.md`（Agent 执行拆解前必须读取该文件）。

**两阶段拆解模式（参考 oh-story 拆书方法论）：**

1. **快速预览**：Agent 先拆前3章 + 整体结构，生成预览报告（基本信息 + 5维评分 + 文风摘要 + 3-5个精选段落 + 适配度评估），用户确认方向
2. **深度拆解**：用户确认后，Agent 按选定档位全量拆解

**入池深度档位（影响token消耗）：**
- 轻量：Planner + Author DNA（约增加 2-3KB/章）
- 标准：以上 + Reference 精选段落（约增加 4-6KB/章）
- 全量：五项全拆（约增加 8-12KB/章）

**方案选项：**
1. **最低投入**：选1本 + 快速预览 + 轻量档拆解
2. **推荐方案**：选3本 + 重点拆1本全五项 + 另两本拆 Planner+DNA
3. **暂不拆解**：先写起来，后面再补

用户选择后执行：
1. 从 `templates/pools/` 初始化项目的 `素材池/` 目录，并落 `素材池/_status.md`（空池标记：`拆解状态: 未拆解/已拆N本/深度档位`，C 回填）
2. 让用户提供对标书（书名或文本文件）
3. Agent 读取 `templates/pools/拆解方法论.md`，按方法论执行**快速预览**，生成预览报告请用户确认
4. 用户确认后，Agent 按选定档位执行**深度拆解**，内容填入对应池子
5. 拆解完成后进入下一步

### Step 7：确认并进入写作

检查所有文件：
```
novel-config.json      ← 项目档案 ✓
设定/世界观.md          ← 完整世界观 ✓
设定/角色声线.md        ← 完整角色基线 ✓
大纲/卷纲.md            ← 卷纲 ✓
大纲/细纲_第0001章.md      ← 第1章细纲 ✓
故事/真相/           ← 6个状态文件（characters/world/hooks/relationships/objects/timeline）✓
故事/元数据/index.md    ← 章节索引（进度唯一真相源）✓
故事/元数据/chapter_0001.md ← 第1章元数据 ✓
故事/日志/            ← 流程日志目录 ✓
配置/身份/       ← 项目级身份档案（如有）✓
叙事总览/              ← Obsidian 总览骨架 ✓
素材池/_status.md       ← 素材池状态标记（未拆解/已拆解）✓
```

确认后对用户说："项目初始化完成，现在开始写第1章"，进入阶段①。

## 入口 B：导入已有（映射驱动）

用户提供已有文件（设定/大纲/角色/正文），Agent 读取并映射到标准结构。

### Step 1：收集已有材料

向用户确认有哪些文件：
- 世界观设定文档？
- 大纲文档？（卷纲/分章纲/完整细纲）
- 角色设定文档？
- 已写正文？（半成品续写）
- 伏笔/设定追踪文档？

用户提供文件路径后，Agent 逐个读取。

### Step 2：映射到标准结构

**世界观 → `设定/世界观.md`**
- 已有世界观文档：直接复制或重新整理为标准格式
- 散落在正文/大纲中：提取关键设定整理成文档

**大纲 → `大纲/` 目录**
- 已有卷纲 → `大纲/卷纲.md`
- 已有分章细纲 → 每章存为 `大纲/细纲_第N章.md`
- 只有一个总大纲 → 拆分为卷纲 + 逐章细纲（Agent 辅助拆解）
- 没有大纲 → 提示用户"建议先建至少前3章细纲"，或对话快速建立

**角色 → `设定/角色声线.md`**
- 已有角色设定：提取语言习惯/口癖/性格 → 按声线模板补全
- 仅有角色描述（外貌/背景/性格词）：Agent 根据描述推断语言基线，标注"推断项，待实测修正"
- 缺少硬边界和情绪光谱：Agent 补充建议，用户确认

**正文 → `正文/` 目录**
- 已有正文：保持原文件；元数据写入 `故事/元数据/chapter_XXXX.md`（功能三 YAML 迁移，正文保持干净）
- 无正文：跳过

### Step 3：重建 故事/真相/ 状态文件

**原则：从当前章节往前推3章重建状态**（太远了没必要，太近了信息不够）。

> **重要说明：如果只有 1-2 章正文，就按实际章数重建，不必强求3章。** 不要因为凑不够3章而报错或强行编造。

从 `templates/truth/` 复制模板，然后：

- `characters.md` — 读取最近3章正文，提取角色当前位置/情绪/已知信息/携带物品，填入当前状态表；从角色设定提取核心信息填入基线摘要
- `world.md` — 读取最近3章正文，提取当前时间/地点/环境，填入当前状态；从世界观设定提取3-5条核心规则填入规则摘要
- `hooks.md` — 扫描已有正文，提取埋设的伏笔，建立 hooks 表（标注埋设章，含推进状态）
- `relationships.md` — 从已有内容中提取角色关系，建立初始矩阵
- `objects.md` — 扫描正文提取关键道具/物品，建立持有链
- `timeline.md` — 从正文提取故事时间锚点，建立时间线

> 如果只有 1-2 章正文，就按实际章数重建，不必强求3章。

### Step 4：生成 novel-config.json

从已有材料推断书名、题材、视角、字数、基调、已完成章数。**以下两项为必确认项，禁止静默默认：**

- **每章目标字数**：材料中提到（如"每章6000-8000字"）→ 提取并请用户确认；材料未提到 → **必须向用户提问**（这是本项目"未确认字数就开写、产出不合规正文"的根因修复）。写入 config 用 `target_word_count` 单字段：用户给区间 → target 取中点（6000-8000 → 7000）；给单值（如3000）→ 直接用。字数验收按 target±15% 判定，config 不存区间
- **正文命名规范**：确认采用 `第000X章 <标题>.md`（4 位章号 + 空格 + 标题）；已有旧命名正文 → 列出并请用户确认是否重命名

其余字段（视角/基调/卖点/已完成章数等）不确定的标注「待确认」请用户确认。

### Step 5：对标书拆解（同入口A Step 6）

同入口A，向用户展示成本表和选项，用户决定是否拆解。

### Step 6：确认并进入写作

输出项目状态摘要，用户确认后说："项目导入完成，现在开始写第 X 章"，进入阶段①。
